# 执行边界与验证

## 执行授权

读取 XML、JAR 清单、模板和配置键属于准备工作。连接数据库并执行 `ds`、`dsJar`、`sql` 或 `init` 会改变外部状态，执行前必须确认：

- 用户指定或授权了目标环境；
- 数据库标识和公司标记明确；
- 使用的输入、模板与数据库类型已经确认；
- 用户了解会执行初始化 SQL、替换数据或忽略错误等非默认行为。

开发、测试和生产名称不清楚时停止执行。不得根据服务器名称自行判断可以写入。

## 凭据处理

- 优先使用目标环境现有的 `app.xml` 和 bobas `ds`，避免在报告或仓库文件中复制连接参数。
- 不读取或展示与当前目标无关的配置值。
- 运行 core 命令时，不把密码写入脚本、日志、Markdown 或版本控制文件。
- 结果报告只保留数据库类型和不敏感的环境标识，不回显完整连接串、用户或密码。

## 执行前审阅

阅读所选 DS 模板的 `Action/Step/Script`，重点搜索：

```text
DROP
DELETE
TRUNCATE
ALTER
UPDATE
INSERT
-force
-ignore
```

对独立 SQL 编排逐个检查动作、执行条件和失败行为。包含删除、数据覆盖或不可逆转换时，需要比普通补字段更明确的用户授权和备份/恢复条件。

## 后置核验

不要只依赖退出码。按本次增量验证：

| 变化 | 至少核验 |
| --- | --- |
| 新 Model | 表存在、字段完整、主键和索引正确 |
| 新 Property | 列存在、实际数据库类型满足模型语义 |
| 新 Index | 名称、唯一性、字段顺序和方向 |
| BO 元数据 | 对象 code、模型映射、字段映射和父子关系 |
| SQL 初始化 | 对应配置、关系或初始记录的可观察结果 |
| 业务数据导入 | 目标对象存在、关键字段正确、重复策略符合预期 |

经典 `ds` 对已存在字段通常只判断“列是否存在”。如果模型改变了字段长度、类型、默认值或可空性，必须额外查询数据库元数据，并在需要时执行兼容 SQL 编排。

## 失败处理

- 默认在第一个错误处停止，不追加无关重试。
- 使用 `-ignore` 后必须逐项汇总错误，不能以最终进程成功作为整体成功。
- 结构成功而初始化 SQL 失败时，分别报告两个阶段，不重复盲跑整个 JAR。
- 修复模型或 SQL 后，只重跑幂等且范围明确的动作；不确定幂等性时先检查当前数据库状态。
- 不自动执行回滚、删表、删列或恢复备份。
