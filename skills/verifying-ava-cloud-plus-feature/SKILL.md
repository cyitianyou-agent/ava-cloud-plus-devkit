# 验证 AVA Cloud+ 完整功能

## 目标

以用户的业务目标和验收条件为基准，证明受影响的模型、后端、REST、前端、数据库和运行行为组成同一条可用链路。验证发现问题时指出断点和责任阶段，不通过修改声明文件、跳过测试或扩大实现范围掩盖失败。

本 Skill 是完整开发流程的最后阶段，也可在数据库执行前作为构建门禁使用。数据库环境未授权或不可用时，只给出已验证部分和未验证部分，不能报告完整验收通过。

## 开始前收集证据

读取目标项目 `AGENTS.md`、版本控制差异、原始需求或交付契约，以及目标项目真实构建入口。确认：

- 本次模型增量和最终 `Domain` XML；
- 受影响的 Java BO、Repository、REST、资源和测试；
- 受影响的 TypeScript `api`、`borep`、`bsapp`、`bsui/c` 与注册；
- 数据库是否已应用本次结构和初始化内容；
- 哪些验收条件需要数据库、服务或浏览器环境。

按 [跨层验收矩阵](references/acceptance-matrix.md) 选择与需求有关的检查，不为未受影响层制造工作。

## 验证顺序

### 1. 差异与范围

检查 `git status` 和最终差异，区分用户原有改动、本次实现、生成候选和构建产物。确认没有凭据、数据库配置、`3rdparty` 声明修改、无关格式化或未审阅的生成覆盖。

### 2. 模型与代码契约

从最终 XML 的对象、模型、字段和关系开始，逐项核对 Java 和 TypeScript。重点检查名称、映射、类型、对象 code、主子键、集合归属、查询保存契约及序列化注册。

### 3. 服务与界面链路

核对 App/Svc Repository、实现、REST、Resolver、前端 Repository、Application、`I...View`、PC View、Console、Mapping、Navigation 和语言资源。只检查本次需求实际需要的入口。

### 4. 构建与自动化测试

按依赖方向运行最小充分验证：

1. XML 与静态一致性检查；
2. 后端核心 JAR 单元测试或编译；
3. 受影响 service WAR 构建；
4. TypeScript `api → borep → bsapp → bsui/c` 构建；
5. `git diff --check` 和最终状态检查。

构建命令必须取自目标项目说明和脚本，不照抄占位模块名。

### 5. 数据库与运行行为

数据库已经授权并应用时，验证结构、BO 元数据、初始化结果，然后执行与验收条件对应的查询、保存、重新加载、规则、正反向影响、回滚和界面流程。环境不可用时保留可复现的未运行清单。

## 判定规则

- **通过**：验收条件的全部必要层都有一致实现和成功证据。
- **部分通过**：静态契约和构建通过，但数据库、服务或界面运行验证因明确环境条件未执行。
- **失败**：存在契约断链、构建失败、数据库不一致或业务行为与验收条件不符。
- **不适用**：经需求范围判断该层不受影响；不能用“不适用”替代缺少实现。

生成器成功、单层编译成功、HTTP 返回成功或页面可以打开，都不足以单独判定完整功能通过。

## 完成标准

- 每项验收条件都有“通过、部分通过、失败或不适用”结论及证据。
- XML、Java、REST、TypeScript 和数据库中的同一语义可以追踪，命名与映射没有断链。
- 主对象、子表和孙表能够按需求保存并重新加载，或明确列为未运行。
- 错误、权限、校验和事务行为按需求验证，而非只覆盖成功路径。
- 最终差异没有生成物、凭据、无关改动或为了通过编译而引入的绕过。
- 失败项指出应返回业务建模、代码生成、后端、前端还是数据库阶段修复。
